### BUG-001 — New move from mid-history appends to end of line instead of truncating
**Scenario:** N2, X1
**File:** `src/store/slices/gameSlice.ts`, `makeMove`, lines 181-197
**Root Cause:**
When the user is at position mid-line (e.g. after move index 1) and plays a new move that doesn't match the existing next move (`currentLine[nextIndex]`), the code does:
```ts
const newLine = [...currentLine, newNode];
```
This appends the new node to the END of the entire current line, e.g. `[e4, e5, Nf3, **d4**]` instead of truncating after the current position and creating `[e4, e5, **d4**]`. This corrupts the move tree.

**Proposed Fix:**
Slice `currentLine` up to and including the current node (`nextIndex`), then append:
```ts
const newLine = [...currentLine.slice(0, nextIndex), newNode];
```

**Status: FIXED**

### BUG-002 — Variation lookup checks wrong node when playing from mid-tree
**Scenario:** N2
**File:** `src/store/slices/gameSlice.ts`, `makeMove`, lines 148-159
**Root Cause:**
The code checks whether the new move already exists as a variation:
```ts
const currentNode = currentLine[lastSeg.index];
if (currentNode) {
  for (let vi = 0; vi < currentNode.variations.length; vi++) {
    if (currentNode.variations[vi][0]?.uci === uci) { ... }
```
`currentNode.variations` holds alternatives that were alternatives to `currentNode` itself (from the position BEFORE `currentNode`). But when the user makes a new move from the current position, we need to check if it exists as a variation of the **next** node — i.e. `existingNext.variations[vi][0]?.uci === uci`. If `existingNext` exists, its `variations` hold alternative first moves from the same position (after `currentNode`).

**Proposed Fix:**
Check `existingNext.variations` instead, and navigate into that variation if found:
```ts
if (existingNext) {
  for (let vi = 0; vi < existingNext.variations.length; vi++) {
    if (existingNext.variations[vi][0]?.uci === uci) {
      const newPath: NavigationPath = [
        ...navigationPath.slice(0, -1),
        { ...lastSeg, index: lastSeg.index + 1 },
        { variationIndex: vi, index: 0 },
      ];
      const varNode = existingNext.variations[vi][0];
      set({ navigationPath: newPath, currentNode: varNode, currentFen: varNode.fen });
      return;
    }
  }
}
```

**Status: FIXED**

### BUG-003 — Loading a second PGN does not clear explorerData or engineOutput
**Scenario:** P4
**File:** `src/store/slices/gameSlice.ts`, `loadPgn`, lines 105-121
**Root Cause:**
`loadPgn` sets `moveTree`, `metadata`, `nodeMap`, `navigationPath`, `currentNode`, and `currentFen`. It does NOT call `clearEngineOutput()` or `clearExplorer()`. After loading a new game:
- `engineOutput` still shows stale analysis from the previous position
- `explorerData` still shows the previous position's moves until a FEN-change fetch completes

The `currentFen` changes to the new game's `rootFen`, which triggers `useEngine`'s FEN subscription (clears engine output via `clearEngineOutput`) and `useExplorer`'s FEN subscription. So the engine output IS cleared correctly via the hook subscription. However `explorerData` is not cleared — the old data stays visible until the new fetch resolves, which can take 300ms+ and may show stale moves with a `loading` indicator.

**Proposed Fix:**
Call `clearExplorer()` in `loadPgn`. Since `loadPgn` is in `gameSlice` but `clearExplorer` is in `explorerSlice`, they share `get()` and `set()`. Use `set` to clear explorer data directly:
```ts
set({
  moveTree: tree,
  metadata,
  nodeMap,
  navigationPath: [],
  currentNode: null,
  currentFen: tree.rootFen,
  explorerData: null,
  explorerError: null,
});
```

**Status: FIXED**

### BUG-004 — AbortError catch does not reset explorerLoading to false
**Scenario:** E5
**File:** `src/store/slices/explorerSlice.ts`, `fetchExplorer`, lines 37-44
**Root Cause:**
```ts
} catch (err: unknown) {
  if (err instanceof Error && err.name === 'AbortError') return; // stale request — ignore
```
When a request is aborted (FEN changed mid-flight), the catch block returns early WITHOUT calling `set({ explorerLoading: false })`. So `explorerLoading` stays `true` indefinitely. The UI shows "Explorer ·" (loading indicator) and the panel shows `ActivityIndicator` forever, until another fetch succeeds.

**Proposed Fix:**
Reset `explorerLoading` before the early return:
```ts
if (err instanceof Error && err.name === 'AbortError') {
  set({ explorerLoading: false });
  return;
}
```

**Status: FIXED**

### BUG-005 — No initial explorer fetch on app startup
**Scenario:** E1
**File:** `src/hooks/useExplorer.ts`, lines 18-61
**Root Cause:**
`useExplorer` sets up subscriptions that fire only when `currentFen` or `explorerEnabled` *changes*. At startup, neither value changes (they are initialized to their defaults), so no fetch is ever triggered for the starting position. The opening explorer is blank until the user makes a move.

**Proposed Fix:**
Trigger an initial fetch after subscriptions are set up, if `explorerEnabled` is true:
```ts
// After setting up subscriptions, do the initial fetch
const { explorerEnabled, currentFen, fetchExplorer } = useChessStore.getState();
if (explorerEnabled) {
  fetchExplorer(currentFen);
}
```

**Status: FIXED**

### BUG-006 — MultiPV lines array may contain undefined slots, breaking EnginePanel
**Scenario:** S3
**File:** `src/store/slices/engineSlice.ts`, `_receiveEngineOutput`, lines 60-64
**Root Cause:**
```ts
const arr = [...(prev?.multipv ?? [])];
arr[multipvLineNum - 1] = output.pv;
newMultipv = arr.slice(0, get().multiPvCount);
```
If `multipvLineNum` is 3 but `arr` only has 1 element, `arr[2] = output.pv` creates a sparse array with `arr[1] === undefined`. `EnginePanel` then does `lines.map((line, idx) => <PvLineRow line={line} ...>)` where `line` could be `undefined`, crashing with "Cannot read properties of undefined".

Also in `EnginePanel` line 29:
```ts
: engineOutput?.pv
? [{ ...engineOutput.pv, score: engineOutput.score ?? null }]
```
When `multiPvCount > 1` and `multipv` is being built up, early info lines for multipv line 1 populate `multipv[0]` correctly but also populate `pv`. The fallback `engineOutput.pv` branch is only used when `multipv` is empty; once it has one (possibly undefined) entry, the `multipv.length` check passes.

**Proposed Fix:**
Filter out undefined slots when building `newMultipv`:
```ts
newMultipv = arr.slice(0, get().multiPvCount).filter((line): line is import('../../types/engine').PvLine => line !== undefined);
```

**Status: FIXED**

### Patterns Observed

1. **Missing state resets on transitions** — BUG-003, BUG-004, BUG-005: Actions that transition state (load PGN, abort fetch, mount hook) fail to reset related state in other slices or fire initial effects.

2. **Off-by-one tree navigation** — BUG-001, BUG-002: The `makeMove` logic for divergent moves appends to the wrong position in the line and checks the wrong node for existing variations. Both stem from the same conceptual error of indexing `currentNode` instead of `nextNode`.

3. **Sparse array hazard** — BUG-006: Assigning to a non-contiguous index of a copied array creates undefined slots that are passed downstream to React components without null-checks.

4. **Stub implementation** — BUG-007: An interface method left as a no-op. Low severity since no callers, but creates a false API contract.
